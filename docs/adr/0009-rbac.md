# ADR 0009: Role-Based Access Control with Tenant Scoping

**Status:** Accepted
**Date:** 2026-06-03

## Context

Within each tenant, different users have different privileges (admins manage configuration, editors index documents, viewers only search). We need a permission model that is simple, enforceable in code, and extensible to document-level ACLs.

## Decision

Implement **RBAC** with four roles, scoped to a tenant:
- `TENANT_ADMIN` — manage tenant config, users, API keys
- `EDITOR` — create / update / delete documents
- `VIEWER` — search and read documents
- `SERVICE` — machine-to-machine (ingestion pipelines, internal callers)

Roles are encoded as JWT claims (`roles: ["EDITOR"]`). Enforcement uses Spring Security `@PreAuthorize("hasRole('EDITOR')")` annotations on controllers. A `TenantSecurityFilter` runs before authorization to ensure the JWT's `tenant_id` matches the request's tenant identifier.

Document-level ACLs are stored as `acl_users` and `acl_roles` fields on each OpenSearch document, filtered at query time, to support fine-grained sharing in the future without re-architecting.

## Consequences

**Positive**
- Standard, declarative, auditable; clear permission matrix in the README.
- Cross-tenant access is impossible by construction (JWT-tenant must match request-tenant).
- ACL extension path is clear — add the fields now, switch on filtering when product needs it.

**Negative**
- Coarse-grained until ACLs are switched on (acceptable for v1).
- JWT must carry roles → larger tokens; mitigated by keeping role names short and not embedding scopes.

**Permission matrix**

| Action | VIEWER | EDITOR | TENANT_ADMIN |
|---|---|---|---|
| GET /search | ✓ | ✓ | ✓ |
| GET /documents/{id} | ✓ | ✓ | ✓ |
| POST /documents | ✗ | ✓ | ✓ |
| DELETE /documents/{id} | ✗ | ✓ | ✓ |
| Manage tenant config | ✗ | ✗ | ✓ |
