# ADR 0017: Mode A — Bastion-kubectl ES Log Access (Zero Credential Storage)

**Status:** Accepted
**Date:** 2026-06-14
**Layer:** Intelligence Agent

## Context

Many organisations run an ECK (Elastic Cloud on Kubernetes) log stack:

```
Application pods → Filebeat (DaemonSet) → Logstash → Elasticsearch (ECK) → Kibana
```

The Elasticsearch password is auto-generated by the ECK operator and stored in a Kubernetes
Secret. It differs per environment and rotates on ES pod restart.

The agent needs to query these logs to answer real-time operational questions. The naive
approach — store the ES password for each environment in a config file — is impractical:
- Passwords are environment-specific and not shareable across teams
- They rotate, making any stored copy stale
- Centralising them creates a high-value credential store as a target

The agent typically has (or can have) SSH access to a bastion host that can reach cluster(s) via
kubeconfig — the same path engineers already use for manual `kubectl` operations.

An additional constraint: the ES external ingress URL (used to reach Kibana from a browser) is
often **not reachable from inside the cluster/bastion network** — it routes via external load
balancer. The ES ClusterIP service is only reachable from inside the cluster.

## Decision

Use **Mode A: bastion-kubectl** as the default transport for ECK deployments.

The agent:
1. SSHes to the bastion (`ssh user@bastion "bash -s" < script`)
2. Runs a shell script that:
   a. Fetches the ES password from the k8s Secret (`kubectl get secret ... | base64 -d`)
   b. Finds a running Filebeat pod (`kubectl get pods -n elastic-system`)
   c. Executes `curl` inside that pod against the ES ClusterIP (`kubectl exec ... curl`)
3. Parses the JSON response
4. **The password exists only in RAM on the bastion for the duration of one kubectl exec call**

ES credentials are **never** stored in the agent's config files, database, or logs.

**Zero-hit namespace retry:** If the configured `k8s_namespace` filter returns 0 hits, the
query is automatically retried without the namespace filter. A warning is surfaced to the user
to update the config.

**Mode B (secondary):** Direct HTTP to an externally-exposed ES endpoint is supported via
`elastic_url` in the environment config. Used for non-ECK deployments or when the external URL
is directly reachable from the agent machine.

## Implementation Notes

The bastion script template uses Python `.format()` for env-specific substitution. kubectl
jsonpath expressions use `{{.data.elastic}}` in the Python template (two braces) which collapse
to `{.data.elastic}` (one brace) after `.format()` — the correct kubectl jsonpath form. Shell
default-value expansions like `${VAR:-default}` cannot coexist with `.format()` because `{VAR:-}`
looks like a format key; the script exports env vars at the top and uses plain `$VAR` references.

## Consequences

**Positive**
- **Zero credential storage** — no ES passwords anywhere in the agent's config, code, or logs.
- **Works for all ECK environments** — as long as the bastion has kubeconfig for the cluster,
  no extra registration is needed for ES access.
- **Handles rotation automatically** — always fetches the current value from the k8s Secret.
- **Uses existing access model** — no new permissions; reuses the bastion + kubeconfig path
  the team already uses for manual operations.
- **Works with ClusterIP** — accesses the internal Service, bypassing ingress entirely.

**Negative**
- **Latency** — SSH + kubectl exec + curl adds ~2–4s per log query. Acceptable when LLM
  generation already takes 20-40s.
- **SSH dependency** — if the bastion is unreachable or kubeconfig is stale, log queries
  fail. Fallback: direct pod log tailing via `kubectl logs`.
- **Script complexity** — multi-step shell heredoc; changes require careful testing of the
  Python-format → shell-expand interaction.

**Neutral**
- Mode B (direct HTTP) is available for non-ECK deployments.
- The SSH key must be mounted into the agent container (configure via `SSH_KEY_PATH` in `.env`).

## Alternatives Considered

| Alternative | Rejection reason |
|---|---|
| Store ES passwords per-env in config | Env-specific, rotate on restart, impractical to collect and maintain |
| External ES ingress URL | Not reachable from bastion/cluster network in most setups |
| ES API key (per-service) | Requires manual creation and rotation per env — same problem as passwords |
| Vault / secrets manager | Requires Vault infrastructure; overkill when k8s Secrets + kubeconfig already exist |
| kubectl port-forward tunnel | Requires long-lived SSH tunnel per env; fragile for a query-time fetch |
